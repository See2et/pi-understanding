## 0. 要約（結論を先に）

1. **目的を「コード理解」から「モデル所有（model ownership）」に移す。** ユーザーが身につけるべきなのは、AIと一緒に作っているソフトウェアの **概念・ルール・境界・状態と振る舞い・判断理由** を、自分の言葉で説明し、未見の状況で予測し、変更提案がモデルのどこを動かすか判断できることである。コードとテストは、モデルを検証するための根拠として必要なときに読む。それ自体を教材の本体にはしない。
2. **現在の設計は「利用者フロー → 責任 → 重要関数 → 契約 → テスト」というコード地図を目的にしている**（`src/learning.ts:67`、`src/extension.ts:218`）。M番号の地図とチャットの組み合わせなので、学習者は受け身になりやすい。何を理解したかも残らない。
3. 5つのUX問題には、それぞれコード上の具体的な原因候補がある。特に影響が大きいのは次の2つ。
   - **スクロール**: fullscreen では、ホイールがペインに届いても `handleMouse` が `undefined` を返して見送る（`src/pane.ts:54-59`、`tests/pane.test.ts:47`）。その結果、ペイン本文はホイールでは動かない【推論】。PgUp/PgDn の案内はペイン下部に出ていない（`src/pane.ts:117`）。
   - **「取得していないので分かりません」**: 学習AIにはツールがない（`src/learning.ts:111`）。送信は約45KBまでで、ファイル名のヒューリスティックで先頭から詰める（`src/scope.ts:131`、`src/scope.ts:158-169`）。このrepository自身で机上計算すると、README とテストの一部で予算が埋まり、`src/` の中核ファイル（extension/learning/scope/pane）は概観時に1つも送られない【推論・未実測】。
4. **推奨案（A）は「モデル台帳 + 根拠オンデマンド」。** 型付きの主張（claim）を並べた台帳を全体像とし、カード → 署名/テスト/局所コード → 全体、と自由に行き来できるようにする。問い（予測・比較・説明・反例・変更判断）はいつでも任意で、スキップできる。学習AIにツールは渡さない。そのかわり拡張が仲介する読み取り専用の根拠取得ループを設け、固定snapshotの中から根拠を取りに行けるようにする。worktree系scopeは、捕捉時点の内容をGitのobjectとして固定する（snapshot-as-tree）。これにより、過去の状態を偽装せずに後から追加で読めるようにする。
5. **操作は「文字は常に入力欄、移動は非印字キー」に統一する。** Tab/Shift+Tab で操作対象を切り替え、↑↓で選び、Enter（入力欄が空のとき）で開き、Esc で一段戻る。スクロールキーは PgUp/PgDn、Ctrl+Home/End、Ctrl+Shift+↑↓ で、Pi本体のtranscriptと同じ語彙にする。fullscreen ではホイールも使える。起動は `/u` を基本にし、補助キーはユーザーと決める。Ctrl+Alt+U は互換として残すだけにする。
6. 代替案として、B「問い駆動チャット（最小変更）」と C「別プロセスの学習セッション（破壊的）」を比較した（§6）。Bの修正（スクロール・キー・根拠取得）は、Aの段階1〜2としてそのまま先に出せる。
7. 段階は 0（再現と計測）→ 1（移動・スクロール・起動）→ 2（根拠オンデマンド）→ 3（snapshot-as-tree と保存形式v2）→ 4（モデル台帳と問い）→ 5（repository単位の台帳と変更起点）とする。各段階に振る舞いの受入れ条件と、学習成果の確認方法（n=1の試用。効果は未測定）を置く（§8）。

## 1. 目的と学習成果

### 1.1 出発点にするユーザーの言葉

> 持たせたいのはcode ownershipというよりもmodel ownership。ユーザーには具体的なコードを把握させたいのではなく、自分がAIを使って開発しているソフトウェアのモデルを把握させたい（もちろん、その手段として必要なときにコードを理解させるのはOK）。

この発言から、次の3点を前提として受け取る。

- 主語は「AIを使って開発しているユーザー」。コードの大部分は自分で書いていない、あるいは書いた記憶が薄い。
- 対象は「ソフトウェアのモデル」。コードの字面ではない。
- コード理解は手段として許される。ただし目的にしてはいけない。

### 1.2 「モデル所有」の定義

タスクで示された仮定義は「モデルの概念/ルール/境界/状態・振る舞い/判断理由を説明・予測・変更判断できること」だった。本提案はこれを採用したうえで、2点を補う。

> **定義（本提案）**: ユーザーがあるソフトウェアのモデルを所有しているとは、次の状態をいう。
>
> 1. そのソフトウェアの **概念**（何が存在するか）、**ルール**（何が常に成り立ち、何が禁じられるか）、**境界**（責任・信頼・時間・データがどこで切り替わるか）、**状態と振る舞い**（入力や出来事に対してどう動き、どう失敗するか）、**判断理由**（なぜそうなっているか、何と引き換えか）を、自分の言葉で **説明** できる。
> 2. 未見の状況での振る舞いを **予測** できる。自信がないときは、何が分からないかを言える。
> 3. 提案された変更が、モデルのどの要素を動かし、どの要素を壊しうるかを **判断** できる。
> 4. （補足1: 検証可能性）主要な主張について、それを確かめる **根拠の所在**（どのテスト・契約・コード片か）を知っている。暗記している必要はない。
> 5. （補足2: 所有者としての意見）「自分の理解が誤っている」ことと「現状は理解したうえで、こうあるべきだと思う」ことを区別して扱える。

補足を足した理由は次のとおり。

- **補足1（検証可能性）**: モデルはソフトウェアを要約したもので、必ずどこかを省いている。AIが作ったモデルの説明を鵜呑みにしても、所有したことにはならない。「この主張はこのテストが守っている」「この境界はこの関数の早期returnで実装されている」と言える状態があって初めて、AIの説明が誤っていたときに気づける。一方で、全関数を把握することは目的にしない。ここで要るのは「どこを見れば確かめられるか」であって、コードの暗記ではない。
- **補足2（意見の区別）**: 所有者は理解するだけでなく、決める立場にある。AI主導の開発では、AIが作った仕様を「理解した」と「承認した」の区別が曖昧になりやすい【仮説】。学習ツールが「理解の誤り」として意見を潰したり、逆に誤解を「意見」として通したりすると、所有は成立しない。

### 1.3 「モデル」に含めるもの・含めないもの

| 要素 | 意味 | pi-understanding 自身の例（根拠） |
| --- | --- | --- |
| 概念 | 存在するもの・状態の単位 | Scope＝固定した理解対象。identityは repository・kind・base/head・snapshot から作る（`src/scope.ts:154-155`） |
| ルール | 常に成り立つこと・禁止 | 学習AIにはツールを渡さない（`src/learning.ts:111`、`tests/contracts.test.ts:92`） |
| 境界 | 責任・信頼・時間・データの切替点 | worktreeの未収集ファイルは後から読めない（`src/scope.ts:88-89`） |
| 状態と振る舞い | 出来事への反応・失敗 | scope切替で実行中の学習呼出しを中止し、古い結果は保存しない（`src/extension.ts:73-82`、`src/learning.ts:97,105`） |
| 判断理由 | なぜそうか・何と引き換えか | 過去の根拠を後から書き換えないため、worktreeを読み直さない（README:92,106。理由はREADME上の記述で、コードからは推論） |

**ドメインモデルだけに限定しない。** pi-understanding の場合、本質的なモデルの大半は業務ドメインではない。snapshotの一貫性、会話の分離、認証経路、並行性（generation）といった技術的・運用的なモデルである。ドメインモデルに絞ると、所有者が変更判断に必要な半分を落とす。

**含めないもの**: ファイル名や行番号の暗記、全関数の網羅、構文の理解。これらは必要なときにツールが示す。

### 1.4 学習成果（観察可能な行動として）

学習が進んだかどうかは、次の行動で見る。

1. **説明**: 主要なルール3つと境界2つを、ツールを見ずに自分の言葉で書ける。内容は根拠と矛盾しない。
2. **予測**: 「scope切替中に学習AIが回答中だったら、その回答はどうなる？」のような未見の状況に答えられる。答えられない場合は、どの情報が足りないかを言える。
3. **変更判断**: 「学習AIにファイル読取ツールを渡す」という変更が、どのルール・境界を動かすかを列挙できる。
4. **根拠の所在**: 上の各主張について、確認できるテストかコードの場所を、ツールで1〜2操作以内にたどれる。
5. **区別**: 自分の誤解を「更新」として扱い、仕様への異論を「意見」として記録し、必要なら実装AIへ明示的に渡せる。

これらの効果は**未測定**である。§8で、n=1の試用で確かめる方法を提案する。

## 2. 現状の診断（根拠付き）

### 2.1 現在の設計が暗黙に置いている目的

- 【事実】学習AIの system prompt は「read-only Japanese code-understanding tutor」で、「Explain user flow -> responsibilities -> important functions/contracts/tests」を求めている（`src/learning.ts:67`）。
- 【事実】map 生成の依頼文は「1-3行の概要、3-5段階の利用者フロー、重要な5-7点…契約・失敗・テスト・正確な根拠」（`src/extension.ts:218`）。
- 【事実】mapの単位 `MapNode` は `flow / responsibility / symbol / contract / tests / evidence`（`src/learning.ts:6`）で、最大12点、各点の根拠は1〜6件、各根拠は60行以内（`src/learning.ts:36,42,47`）。
- 【推論】この設計の目的は「重要関数とその契約・テストの地図」、つまりコード中心の理解である。「ルール」「境界」「判断理由」は型として存在せず、`contract` の自由文に含まれるかどうかもAI次第になる。
- 【事実】理解したかどうかの記録はない。`Learning` 型にあるのは会話、map、焦点、publication、milestone質問の既出キーだけ（`src/learning.ts:22`）。
- 【事実】理解確認は「milestoneでの任意の質問」1件に限られ、実装AIの `publish_understanding` か `ALLOW_ONE_QUESTION` を経由した場合だけ出る（`src/extension.ts:275`、`src/learning.ts:131`）。

**良い性質（後で維持する）**: 引用の機械照合（`src/learning.ts:43-50`）、会話分離（`src/learning.ts:86-89`、`tests/contracts.test.ts:84-104`）、scope切替時の世代管理（`src/extension.ts:54-57,73-82`、`tests/extension.test.ts:82-190`）、branchを考慮したrestore（`src/learning.ts:27-34`、`tests/contracts.test.ts:74-82`）、端末制御文字の除去（`src/pane.ts:6`、`tests/pane.test.ts:69-72`）。

### 2.2 問題1「チャットできるがスクロールできず遡れない」

実機での再現はしていない。原因は断定しない。候補と、その検証方法を示す。

**事実**

- 【事実】ペイン本文はひとつのMarkdownである。「マップ（または選択点の詳細）→ 焦点・根拠 → 学習チャット」を連結して描画し（`src/pane.ts:101-106`）、`offset` で切り出す（`src/pane.ts:109-114`）。会話だけを独立してスクロールする領域はない。
- 【事実】PgUp/PgDn の意味がモードで反転する。`followChat` のときは下端からの距離、そうでないときは上端からの距離として扱う（`src/pane.ts:67-68,113`）。モードは送信・dive・overview・選択変更のたびに切り替わり、offsetは0に戻る（`src/pane.ts:36,50-51,66,91`、`src/extension.ts:95`）。
- 【事実】ペイン下部の案内は「Ctrl+Alt+U 表示/入力切替 / Esc 通常 / Ctrl+T 対象（または Ctrl+C 中止）」だけで、PgUp/PgDn は出ていない（`src/pane.ts:117`）。PgUp/PgDn はHELP（`src/extension.ts:33`）とREADME（README:76）にしか書かれていない。QAの描画結果でも、下部にスクロールの案内はない（`.evidence/native-qa/learning-dialogue-120x36.txt:32`。fixture providerでの描画）。
- 【事実】ホイール・ドラッグ・右クリックは処理せず `undefined` を返す（`src/pane.ts:54-59`）。テストもそれを期待している（`tests/pane.test.ts:47`）。
- 【事実】Pi の fullscreen では、ホイールを最前面のoverlayへ先に配送する。overlayが `undefined` を返すと、overlayにフォーカスがあれば viewport 側は処理を見送る。フォーカスがなければ、背後の transcript の ScrollView をスクロールする（`node_modules/@earendil-works/pi-tui/dist/tui-alt-screen.js:497-513`、`tui-alt-screen.js:793-806`、`tui.js:508-532`）。
- 【事実】Pi docs: 「Regular mode leaves mouse input to the terminal because the terminal owns scrollback」（`docs/tui.md:62`）。
- 【事実】fullscreen では、overlayにフォーカスがあるとき PageUp/PageDown 等の transcript 操作はoverlayに譲られる（`tui-alt-screen.js:461-463,546-547`）。したがって、フォーカスがあれば PgUp/PgDn はペインの `handleInput` に届くはず【推論】。
- 【事実】ペインは注入される `KeybindingsManager` を無視し（`src/extension.ts:103` の `_kb`）、`matchesKey` で固定キーを判定している（`src/pane.ts:62-68`）。Pi docs は、拡張コンポーネントが注入された KeybindingsManager を使うよう求めている（`docs/tui.md:46`）。
- 【事実】保存されるのは最新40件・約6万文字までで、それより古い会話は消える（`src/extension.ts:66-67`）。モデルに送る履歴はさらに16件・1.6万文字（`src/learning.ts:82-85`）。
- 【事実】native QA は「reload後にPgDnを10回送ってfailure表示が見える」ことしか確かめていない（`tests/native-qa.py:147`、`tests/render-captures.mjs:75`）。長い会話をPgUpで遡れるか、ホイールで動くかは検証対象になっていない。

**原因候補（未検証。可能性が高いと考える順）**

| # | 候補 | 根拠の種類 |
| --- | --- | --- |
| S1 | ホイールやトラックパッドでスクロールしようとした。fullscreen ではペインが見送り、本文は動かない（フォーカスがなければ背後のtranscriptが動く）。regular では端末のscrollbackが動き、ペインは動かない | 事実からの推論 ＋ 操作方法は仮説 |
| S2 | PgUp/PgDn の存在が見えていない（下部に案内がない） | 事実 ＋ 仮説 |
| S3 | キーボードにPgUp/PgDnがない、または Fn との組み合わせで送れない（ノートPCやmacOS） | 仮説 |
| S4 | PgUpの方向がモードで変わるうえ、送信やdiveのたびにoffsetが0に戻る。そのため「遡っていたのに戻された」と感じる | 事実からの推論 |
| S5 | 遡りたい会話が保存上限で既に消えている | 事実（上限）＋ 該当したかは仮説 |
| S6 | tmux・mosh・IDE端末が PgUp を奪っている、または変換している（`docs/terminal-setup.md:5`） | 仮説 |
| S7 | ペインにフォーカスがない（Ctrl+Alt+U後の状態の取り違えなど）ので、PgUp が背後の transcript に行っている | 推論 ＋ 仮説 |

**検証方法（段階0）**

1. ユーザーに確認する: fullscreen か regular か、端末と多重化（tmux/mosh）の有無、スクロールに使った操作（ホイール、トラックパッド、PgUp、Fn+↑）。
2. PTY QA を足す: 3画面以上の会話を作り、(a) PgUpを繰り返して最初の質問文が見えるか、(b) fullscreen で SGR のホイール上方向（`\x1b[<64;x;yM`）をペイン上で送って本文が動くか、背後の transcript が動くか、(c) 送信直後に PgUp で遡れるか、を両モード・3サイズで捕捉する。S1が正しければ (b) が失敗するはずである。
3. KeybindingsManager で PageUp を再割当てした状態でも、ペインが期待どおり動くかを見る。

### 2.3 問題2「dive N が不便。Tabなどで移動したい」

- 【事実】選択点へ移動するには `dive N` を入力欄に打つか、`/understand dive N` を実行する（`src/extension.ts:90-94,220`、`src/pane.ts:36`）。一覧から選ぶUIはない。
- 【事実】上部のminimapには `M1 … M12` の番号しか出ない（`src/pane.ts:94-96`）。番号の意味は本文の全体図を読まないと分からない。
- 【事実】`Input` は Tab・↑・↓ を処理しない。制御文字として捨てている（`node_modules/@earendil-works/pi-tui/dist/components/input.js:74-183`）。つまりペインはこれらのキーを移動に使える。
- 【事実】フォーカスしたoverlayは、拡張ショートカットやアプリのキーより先に入力を受ける。Ctrl+Alt+U がペインの `handleInput` に届くこと自体が、その例になっている（`src/pane.ts:61-62`、`tests/pane.test.ts:44`、`tests/native-qa.py:103-109`）。Shift+Tab（本来は thinking 切替。`docs/keybindings.md:155`）も同様にペインへ届くと推論する【推論・未検証】。
- 【推論】数字や英字キーで選ぶ方式は、日本語IMEがONのときに全角化されたり変換に取られたりする。非印字キー（Tab・矢印・Enter・Esc）なら、IMEが確定済みのときは素通りする【仮説：IMEの実装による】。

### 2.4 問題3「Ctrl+Alt+U を使いたくない」

- 【事実】起動・切替の主経路は Ctrl+Alt+U で、`registerShortcut` で固定 KeyId として登録している（`src/pane.ts:7-8`、`src/extension.ts:168-176`）。`registerShortcut` の型は固定 KeyId を受け取るだけで（`node_modules/@earendil-works/pi-coding-agent/dist/core/extensions/types.d.ts:1198-1201`）、ユーザーの `keybindings.json` で再割当てできる「action」ではない【推論】。
- 【事実】native QA は Ctrl+Alt+U を CSI-u（`\x1b[117;7u`）で送っている（`tests/native-qa.py:100`）。修飾キー付きの入力は、端末・tmux・IDE端末で失われることがあると Pi docs にある（`docs/terminal-setup.md:5`、`docs/tmux.md:3`）。
- 【仮説】3キーの同時押しは手に負担がかかる。macOS の Option は Meta として送られない設定も多い。
- 【事実】`/understand` にはサブコマンドの補完がない（`src/extension.ts:177-179`。`getArgumentCompletions` は `types.d.ts:1140` で利用可能）。
- 【事実】通常editorに下書きがある状態では、`/understand` を打つにはその下書きを消す必要がある（Piのslash commandは入力欄から実行する）。ショートカットはそれを避けるために存在する【推論】。

### 2.5 問題4「『今回は取得していないので分かりませんが』が多い」

- 【事実】学習AIにはツールがない（`src/learning.ts:111` の `tools: []`、`tests/contracts.test.ts:92`）。system prompt は「欠けた根拠を開示し、省略ファイルを分析したふりをするな」と指示している（`src/learning.ts:67`）。このため、AIが根拠を取りに行けず「分からない」と言うのは、**設計どおりの正しい振る舞い**である。
- 【事実】収集上限は120ファイル・合計300KB・1ファイル24KB（`src/scope.ts:8`）。収集順は「変更ファイル → 名前が README/index/main/test/spec に一致するもの → その他」（`src/scope.ts:131`）。上限を超えたファイルは黙って飛ばし、未収集数に数えるだけ（`src/scope.ts:140-142,152`）。
- 【事実】モデルに送るのは約45KBまで。その順で、入らないブロックは `continue` で飛ばす（`src/scope.ts:158-165`）。dive中は選択点の根拠ファイルを先頭に置く（`src/learning.ts:72-73`）。それ以外の順序は、質問との関連とは無関係である。
- 【事実】mapの根拠照合は「今回送ったsource」だけを対象にする（`src/learning.ts:124` の `parseReply(text, context.sent)`）。したがって、送られていないファイルはmapの根拠になりえない。
- 【事実】worktree系scope（changes/repository/module）で未収集のファイルは、後から読めない（`src/scope.ts:88-89`、README:106）。履歴系scope（commit/PR/branch）は、固定したbase/headから追加で読める（`src/scope.ts:91-98`）。ただし読めるのはユーザーが `/understand reference` を明示した場合だけで（`src/reference.ts:5-20`）、AIからは要求できない。
- 【推論・未実測】**机上計算**（このrepository自身を `repository` scopeにした場合）: 収集順は README.md（20.5KB）→ tests/* → その他。送信時に行番号の接頭辞が加わり、README とヘッダで約22KB、`tests/contracts.test.ts`（10.2KB）を足して約33KB になる。`tests/extension.test.ts`（16.3KB）は入らないので飛ばす。その後は小さいファイルで残りが埋まる。`src/extension.ts`（23.2KB）、`src/learning.ts`（15.7KB）、`src/scope.ts`（13.9KB）、`src/pane.ts`（10.8KB）は、概観時の送信には1つも入らない。結果として、全体mapは主にREADMEとテストを根拠に作られる。READMEは仕様の正当性の根拠にならないので、モデル所有にとって最も避けたい状態である。

### 2.6 問題5「全体 → 重要テスト/関数シグネチャ/局所コードへ進む体験がない。もっとインタラクティブで適度な認知負荷を」

- 【事実】全体図（段階ごとの M番号・flow・責任・symbol・理由）と詳細（契約・テスト文・根拠引用）の2階層しかない（`src/pane.ts:101-102`、`src/learning.ts:17-19`）。「関数シグネチャだけ」「テストのassertだけ」を見る中間の段階はない。
- 【事実】`tests` 欄はAIが書く自由文で、テストの実在や対応関係は照合していない（`src/learning.ts:40` は文字列長だけを検査）。テストを根拠として引用できるのは、テストファイルが送られていた場合だけである。
- 【事実】局所コードを見るには `/understand reference [path [base|head|index] [all|START-END]]` という文法を覚える必要がある（`src/extension.ts:26,222-225`）。結果は会話へ notice として追記され（`src/extension.ts:225`）、会話と根拠が同じ流れに混ざる。
- 【事実】ヘッダは通常5行（root・base/head・snapshot・鮮度）、区切り1行、ナビ2行を使う（`src/pane.ts:83-90,96`）。120x36 の描画では、33行中約9行が本文以外の枠に使われていた（`.evidence/native-qa/learning-dialogue-120x36.txt:3-10,32-33`）。
- 【推論】学習者がすることは「読む」か「問う」のどちらかで、予測・説明・反例といった能動的な活動はツール側から提案されない。認知負荷は、AIの回答の長さとmapの密度でしか調整できない。

## 3. 設計原則

1. **モデルが主、コードは根拠。** 画面の主役は主張（claim）とする。コードは主張の真偽を確かめるために開く。
2. **全体はいつでも1操作で見える。** どの深さにいても、Ctrl+O でモデル全体へ戻れる。Esc は一段ずつ戻る。
3. **能動的に、ただし強制しない。** 問いは常に1つだけ示し、任意でスキップできる。答えを見る、後で、自由質問、のどれを選んでも罰はない。
4. **AIの判定は参考情報で、所有の状態はユーザーが決める。** AIが返すのは根拠付きの照合で、点数は出さない。
5. **分からないなら取りに行く。取れないなら理由を言う。** 「未送信」「固定objectから追加で読める」「捕捉していない作業状態」「除外」「範囲外」を区別して示す。
6. **時間を偽らない。** 主張は、それを確かめたsnapshotに結びつける。別時点の内容を黙って混ぜない。
7. **文字は常に入力欄へ、移動は非印字キーで。** IMEの候補位置が安定し、モード誤りが起きない。
8. **Piの語彙に合わせる。** スクロールは Pi transcript と同じキー（PgUp/PgDn、Ctrl+Home/End、Ctrl+Shift+↑↓）にし、KeybindingsManager の再割当てに従う。
9. **分離と安全の契約は動かさない**（§7.3）。

## 4. 推奨案A「モデル台帳 + 根拠オンデマンド」

### 4.1 モデル台帳（Model Ledger）の構造

M番号のmapを、型付きの主張（claim）の台帳に置き換える。

```ts
// 提案。実装ではない
type ClaimKind = "concept" | "rule" | "boundary" | "behavior" | "rationale";
type Claim = {
  id: string;               // 種類ごとの安定ID: C1 概念 / R1 ルール / B1 境界 / S1 状態・振る舞い / W1 理由
  kind: ClaimKind;
  statement: string;        // 1文（≤200字）。全体画面に出るのはこれだけ
  detail?: string;          // 補足（≤800字）
  basis: "code" | "test" | "doc" | "inferred"; // 何に基づく主張か。rationaleはdoc/inferredが多い
  evidence: Evidence[];     // exact quote 照合済み（既存 validateMap と同じ規則）。inferred は0件可
  guards: TestRef[];        // この主張を守るテスト（test名＋assert行のexact quote）。空なら「守るテスト未発見」
  signature?: Evidence;     // 主張の入口となる関数・型のシグネチャ行（exact quote）
  relations: { to: string; type: "depends" | "protects" | "constrains" | "explains" }[];
  challenge?: Challenge;    // 任意の問い（§4.4）
  verifiedAt: string;       // 照合した scope.snapshot
  origin: "generated" | "dialogue" | "publication" | "user";
};
type Ownership = {          // ユーザーだけが変更する
  state: "unseen" | "read" | "predicted" | "explained" | "doubt";
  opinion?: string;         // 仕様への意見（理解の誤りとは別）
  note?: string;
};
```

- 台帳は1つのscopeにつき8〜20件を目安にする。全体画面では種類ごとに最大5件を表示し、残りは「さらにN件」に畳む。
- AIは主要な主張に「核」印を最大5件付ける。10分の入口の提案だが、ユーザーはどこから始めてもよい。
- `basis` と `evidence` で、事実と解釈を分ける。exact quote の照合で保証されるのは引用の実在だけで、主張の意味が正しいことまでは保証しない。この点は画面でも明示する（既存の注意書き `src/learning.ts:18` を継承する）。
- 「守るテスト未発見」は、それ自体がモデル所有にとって有用な発見になる。ただし「探した範囲で見つからない」ことと「存在しない」ことは別なので、表示文言で区別する。

### 4.4 問いの種類と認知負荷の調整

| 種類 | 例 | 主に効く要素 | 負荷 |
| --- | --- | --- | --- |
| 予測 | 「切替中の回答はどうなる？」 | 状態・振る舞い | 中 |
| 比較 | 「branch scopeとchanges scopeで refresh の意味はどう違う？」 | 概念・境界 | 中 |
| 説明 | 「なぜ学習AIにtoolを渡さない？」 | 判断理由 | 高 |
| 反例 | 「このルールを破る入力を考えて」 | ルール・境界 | 高 |
| 変更判断 | 「この変更でどの主張が動く？」 | 全体（所有） | 高 |
| 確認（足場） | 「R2の根拠を1つ選んで」 | 根拠の所在 | 低 |

調整の仕組み【提案】。学習研究で知られる予測→観察→説明、自己説明、反復想起、worked example の足場外しを**設計上の仮説**として借りる。本プロジェクトでの効果は未測定。

- 問いは1カードに1つだけ示す。台帳全体でも、同時に未回答の問いを溜めない。
- 「分からない」は正当な答えとして扱う。返すのは、その主張の根拠を1つ示した例（worked example）と、より低負荷な足場の問いで、評価はしない。
- 連続して一致した種類では、次から足場を省き、負荷の高い問いを提案する。連続して「分からない」が続いた種類では、負荷を下げる。調整はAIの提案に留め、ユーザーは常にスキップできる。
- 問いを出さないモード（`/u quiet`）を用意する。台帳と根拠を読むだけの自由探索も、正当な使い方とする。

### 4.5 AI判定の不確実性と、理解の誤り／仕様への意見の区別

**照合の出し方**

- 4区分で返す: **一致 / 部分一致 / 不一致 / 判定不能**。どの区分にも、引用元（exact quote）を最低1つ付ける。根拠を示せない場合は「判定不能」とし、［根拠を取りに行く］を提示する。
- 見出しは「AIの照合（誤る可能性あり）」とし、点数や正答率は出さない。
- ［異議］を押すと、ユーザーの答え・主張・根拠を並べて再照合する。それでも食い違えば、両方を残したまま `doubt` 状態にする。所有の状態はユーザーの選択で決まり、AIは提案しかしない。

**区別のフロー**

```
ユーザーの答え・発言が根拠と食い違う
  └─ AI: 「コードの現状:〈引用〉/ あなたの答え:〈要約〉/ 差:〈1文〉」
       ├─ ［理解を更新］ → 主張の状態はそのまま。ユーザーの理解メモを更新
       ├─ ［仕様への意見］ → Ownership.opinion に記録。誤りとは数えない
       └─ ［根拠が古い・違うと思う］ → 根拠の再取得（§4.7）、または doubt
```

- AIは「意見」を「誤り」として訂正しない。system prompt には「Distinguish learner misunderstanding from specification opinion; never treat an opinion as an error」を加える。
- 意見は実装AIへ自動では送らない。送る経路は `handoff` だけで、ユーザーが選び、編集し、確認する（§7.3）。

### 4.6 操作体系: フォーカス、キー、IME、スクロール、戻る、起動、下書き

**基本の規則**

1. **文字（IMEで確定した文字や貼り付けを含む）は常に入力欄に入る。** 入力欄が唯一の `CURSOR_MARKER` を持つので（`docs/tui.md:48-50`）、どの領域を操作していてもIMEの候補ウィンドウは入力欄に出る。英字1文字のショートカットは使わない。
2. **移動は非印字キーで行う。** 「操作対象（台帳・カード／根拠・会話）」は、↑↓や PgUp/PgDn がどの領域に効くかを決める論理的な選択であり、テキストフォーカスとは別である。
3. **Enter は、入力欄が空なら「選択項目を開く・実行」、文字があれば「送信」。**

**キー一覧（提案）**

| キー | 動作 | 備考 |
| --- | --- | --- |
| Tab / Shift+Tab | 操作対象を 台帳 → カード/根拠 → 会話 → ボタン行 の順に循環 | 下書きは保持。Shift+Tab は overlayにフォーカスがあるときペインに届く【推論・要検証】 |
| ↑ / ↓ | 台帳では項目選択、根拠・会話では1行スクロール | Input は↑↓を使わない（`input.js:74-183`） |
| Enter | 入力が空なら開く・実行、文字があれば送信 | 開く＝旧 `dive N` |
| Esc | 一段戻る（根拠 → カード → 全体）。全体で押すとペインを隠して通常入力へ | **現状（即座に隠す、`src/pane.ts:62`）から意味が変わる**。§9で確認する |
| Ctrl+G | どこからでも即座に通常入力へ（下書きを保持） | 現状の契約を維持 |
| Ctrl+O | モデル全体へ一発で戻る | 現状を維持（`src/pane.ts:66`） |
| PgUp / PgDn | 操作対象をページ単位でスクロール（既定は会話） | Pi の `tui.altScreen.pageUp/Down` と同じ語彙。KeybindingsManager に従う |

- ペイン下部の1行には、**現在の操作対象で使えるキーだけ**を出す（たとえば会話を操作しているときは「PgUp/PgDn・Ctrl+Home/End・Ctrl+Shift+↑↓」）。これで S2（案内がない）を直す。
- 会話は独立したスクロール領域にする。読んでいる位置は新しい回答が来ても動かず、「新しい回答 ↓（Ctrl+End）」と表示する。送信直後だけ末尾への追従に戻す。これで S4（offsetが0に戻される）を直す。
- 方向の意味は常に「PgUp＝上（古い方）」に固定する。`followChat` による反転（`src/pane.ts:67-68`）はやめる。
- `dive N` / `overview` / `/understand dive N` は、互換の別名として残す（覚えている人や、スクリプトのため）。

**IMEについて**

- 変換中のキー（↑↓・Tab・Enter）は、通常IME側が消費し、アプリには届かない【仮説：IMEと端末の組み合わせによる】。確定後のキーだけが移動に使われるので、操作対象の切替が変換を壊すことはない。
- 検証はユーザーの実IME（fcitx・ibus・macOSなど）で手動で行う。物理IMEの候補位置は deterministic QA では確認できない（README:156 にも同様の記載がある）。

**起動と切替（Ctrl+Alt+U を必須にしない）**

| 方式 | 内容 | 判断 |
| --- | --- | --- |
| `/u`（`/understand` の短縮） | 前回の場所で開く。scope未選択なら対象一覧、台帳が空なら生成を提案。`/u 質問文` で質問して開く | **推奨（主経路）**。補完（`getArgumentCompletions`）でサブコマンドを示す。コマンド名の衝突は要確認（§9） |

**下書き**

- 学習側の下書きは2種類にする。**自由質問の下書き**（全体で1つ）と、**カードごとの回答の下書き**（その問いに紐づく）。入力欄の左に宛先（「R2への回答」「全体への質問」）を表示し、送り先を取り違えないようにする。
- 現在の native Input をremountしても保持する契約（`src/pane.ts:9-10,31-33`、`tests/pane.test.ts:34-37`、`tests/extension.test.ts:178-184`）は、両方の下書きに広げる。
- 通常editorの下書きはPiが保持しているので、拡張は触れない（現状を維持）。

### 4.7 根拠の適宜取得（読み取り専用）と context 配分

**方式【提案】: 拡張が仲介する取得ループ。学習AIにツールは渡さない。**

1. 毎回の送信に、**領域目録（territory outline）**を入れる。scope内で許可されたファイルのパス・サイズ・状態（§4.8）と、軽量に抽出した先頭レベルの宣言名（export・function・class・test名。正規表現で取り出し、≤8KB）である。AIは「何が存在し、どこにありそうか」を知ったうえで要求できる。
2. 学習AIは、回答JSONに `need` を含めてよい。

   ```json
   {"reply":"（途中経過、任意）","need":[{"path":"src/extension.ts","ref":"head","lines":"60-90","why":"scope切替時の中止処理を確認する"}],
    "search":[{"text":"detachLearning","why":"呼出し元を知る"}]}
   ```

3. 拡張は各要求を検証する（§4.9の安全境界）。通ったものだけを固定snapshotから読み、ユーザーに「根拠を取得中 1/2: src/extension.ts:60-90（理由: …）」と見せてから再度呼び出す。
4. 上限は、1回の質問につき取得2ラウンド・1ラウンド6件・取得量合計24KB・検索ヒット50行・総時間3分とする（数値は初期値。§9で確認）。上限に達したら、取得できたものだけで回答させ、欠けたものは状態付きで明記させる。
5. 取得した根拠は、そのターンの記録に `fetched: [{path, ref, range, digest}]` として残す。後から「この回答は何を読んで書かれたか」を確認できる。

`search` は、固定objectに対して `git grep -n -F --no-textconv -e TEXT <tree-ish> -- <許可パス>` で行う。tree-ish はscopeのhead・base、または §4.8 の snapshot tree。worktreeは読まない。

**なぜネイティブのtool callではないか**: `tools: []` は現在テストで守られた契約で（`tests/contracts.test.ts:92`）、README も学習AIにツールを渡さないことを約束している（README:5）。JSON要求方式なら、何を読むかの決定と検証がすべて拡張側の決定的なコードに残り、ユーザーにも可視になる。将来ネイティブの読み取り専用toolへ移るかどうかは、§6・§9 で再検討できる。

**context 配分（1回の送信。初期値の提案）**

| 枠 | 上限 | 中身 |
| --- | --- | --- |
| 固定 | 約4KB | system prompt、scope identity、台帳の要約（各主張の1文） |
| 領域目録 | 約8KB | パス・サイズ・状態・宣言名 |
| 選択中の主張の根拠 | 約10KB | 選択カードの evidence・signature・guards の周辺 |
| 取得根拠 | 約24KB | `need` / `search` の結果 |
| 会話 | 約8KB | 現在のカードのスレッドを優先し、全体の会話は要約 |

合計は約54KBで、現状の約45KB＋履歴1.6万文字（`src/scope.ts:8`、`src/learning.ts:83`）と同程度に収まる。違いは、**質問との関連で詰めること**と、**足りなければ取りに行けること**である。費用を増やしてよいかはユーザーの判断事項とする（§9）。

台帳を生成するときも同じループを使う。まず目録だけを渡して「読むべきファイル」を選ばせ、次にそれらを読んで台帳を作らせる。これで §2.5 の「READMEとテストだけから全体mapを作る」状態を避ける。

### 4.8 snapshot の設計（過去の状態を偽装しない）

**根拠の状態を区別して表示する**

| 状態 | 意味 | 後から読めるか | 画面表示 | AIへの指示 |
| --- | --- | --- | --- | --- |
| 送信済み | 今回のターンで送った | ― | ✓ | 引用してよい |
| 収集済み・未送信 | scopeに捕捉済みで、予算外 | **読める**（同じバイト列、digestで確認） | ○未送信 | `need` で要求できる |
| 固定object・未収集 | commit/PR/branch の base/head、または snapshot tree に含まれる | **読める**（不変object、digestで確認） | ○追加取得可 | `need` で要求できる |
| 作業状態・未捕捉 | 旧形式のworktree系scopeで捕捉していない | **読めない**。今読むと別の時点になる | ×作業状態 | 「この時点の内容は残っていない。refreshで新しいscope」と言う |
| 除外 | secretらしいpath・生成物・binary・symlink・サイズ超過 | 読めない | ×除外（理由付き） | 理由を言う。推測しない |
| 範囲外 | module scopeの外など | 読めない | ×範囲外 | scope変更を提案する（選択は確認付き） |
| object消失 | 固定objectがGit gcなどで失われた | 読めない | ×消失 | refreshを提案する。偽装しない |

**snapshot-as-tree（worktree系scopeの再設計）【提案】**

- 捕捉時に、許可パス（`allowedPath`、`src/scope.ts:27-29`）の通常ファイルを `git hash-object -w --no-filters` でobjectにし、**一時的な別indexファイル**（`GIT_INDEX_FILE` をrepository外の一時パスにする）で `git update-index --add --cacheinfo` → `git write-tree` を実行して、tree OID を得る。changes scope の index 側は、`git ls-files --stage` の blob OID から同様に tree を作る。
- これで捕捉時点の内容を不変objectとして固定でき、後から `need`・`search`・`reference` で正確にその時点の内容を読める。**本物のindex・HEAD・branch・worktreeは変更しない。** 追加されるのはobject databaseへのloose objectだけで、これは PR scope が既に行っているのと同種の変更である（README:94）。
- `--no-filters` を必須にする。clean filter（`.gitattributes` と git config）を実行させないためで、現状の `--no-ext-diff --no-textconv`（`src/scope.ts:45,127`）と同じ方針である。
- 捕捉の前後で fingerprint を比較し、変化していれば失敗させる（`src/scope.ts:153`）。この競合検出は維持する。atomic snapshot ではない点も、現状どおり明記する（README:105）。
- 【仮説・要確認】参照されないloose objectは、Gitの既定では一定期間後（`gc.pruneExpire`。既定は2週間と理解している。未検証）に `git gc` で消えうる。対策は2案あり、ユーザーに選んでもらう（§9）。
  - (a) refを作らない（既定）。読むときにdigestを照合し、消えていれば「object消失」と表示する。主張の引用文は台帳に残っているので、表示は失われない。
  - (b) `refs/pi-understanding/<scope-id>` のような隠しrefで保護する。`git for-each-ref` に見え、`push --mirror` で外へ出うるため、明示の同意が必要。
- 履歴系scope（commit/PR/branch）は既に不変objectを使っているので、このtree化は不要である。

**鮮度の扱い**

- 主張は `verifiedAt`（snapshot）に結びつける。作業状態が変わったら（`agent_settled` での fingerprint 比較、`src/extension.ts:131-136`）、ヘッダに「作業状態が変化。台帳は HH:MM 時点のモデル」と出す。その時点の主張を、現在の主張として黙って提示しない。
- refresh すると新しいscope（新しいidentity）ができる。段階5では、主張を新しいsnapshotで**再照合**して引き継ぐ。exact quote が同じ行範囲・別の行範囲で見つかれば「再確認済み」、見つからなければ「根拠が変化」と表示し、黙って移さない。

### 4.9 安全境界: secret / path / 量 / 時間 / キャンセル

- **path**: `need`・`search` の対象は、既存の `safePath`（`src/scope.ts:23-26`。絶対パス・`..`・`:`・制御文字を拒否）と `allowedPath`（`src/scope.ts:27-29`）、module scope の包含判定（`src/scope.ts:30-32`）を通す。symlinkと非通常ファイルは拒否する（`src/scope.ts:66-68,93`）。AIの要求は**データ**として扱い、命令としては扱わない（`src/learning.ts:67` の方針を維持）。
- **secret**: `allowedPath` は secret scanner ではない（README:104）。この限界は変わらないので、明記を続ける。取得結果は送信前に画面へ出るので、ユーザーが中止できる。取得を `.env` 等の除外パターンへ広げることはしない。追加として、送信前に高エントロピー文字列や典型的な鍵形式の簡易検出で警告する案を、効果未検証の任意機能として挙げておく。
- **量**: 上記ラウンド・件数・バイト数の上限を設け、ファイルごとの24KB上限（`src/scope.ts:8`）を維持する。大きいファイルは行範囲指定でだけ読めるようにする（≤60行×複数範囲）。
- **時間**: モデル呼出し1回の90秒 timeout（`src/learning.ts:111`）を維持し、質問全体にも3分の上限を置く。git コマンドの20秒 timeout（`src/scope.ts:19`）も維持する。
- **キャンセル**: Ctrl+C で、取得中・推論中のいずれも中止する。中止時は取得済みの根拠を表示に残すが、主張としては採用しない。scope・branch・sessionの切替では、現在の世代管理（`src/extension.ts:73-82`、`src/learning.ts:97,105`）で取得ループごと破棄する。
- **端末**: 取得した内容とAIの出力は、引き続き `terminalText`（`src/pane.ts:6`）で制御文字を除去する。

### 4.10 保存・見直し・既存scopeの移行

**現状の事実**

- 【事実】保存のたびに `structuredClone(state)` を丸ごと `appendEntry` する（`src/extension.ts:69`）。`state` には各scopeの収集source本文（最大300KB×最大6scope）が含まれる（`src/scope.ts:12-16`、`src/extension.ts:161`）。1回の質問で少なくとも開始時と完了時の2回保存する（`src/learning.ts:108,139`）。
- 【推論】session file は、質問1回ごとに数百KB〜MB単位で増えうる。append-only なので、`forget` しても物理的には減らない（README:124）。

**提案**

- 保存形式 v2 を、新しい customType `see2et.pi-understanding.v2` として導入する。
  - worktree系scopeは、tree OID・各sourceのpath/ref/digest・送信済み引用だけを保存し、本文は保存しない。本文は必要時にobjectから読む。object消失時は表示済みの引用だけが残る。
  - 履歴系scopeも同様に、base/head OID と digest だけを保存する。
  - 台帳・所有状態・意見・会話（カードごとのスレッド）を保存する。会話の上限は件数ではなく文字数で管理する。
  - 差分保存（変更されたscopeだけ）を検討する。restoreは `getBranch()` の最新を読む方式を維持する（`src/learning.ts:27-34`）。
- **移行**:
  - restore では、v2 の最新エントリがあればそれを使う。なければ v1 の最新を**メモリ上で変換**し、次の保存から v2 を書く。v1 エントリは書き換えず、以後追記もしない。
  - 旧mapの各点は、台帳の「旧マップ（責任・関数中心）」節に読み取り専用カードとして残す。`flow / responsibility / symbol / contract / tests / evidence` をそのまま表示し、［モデルとして作り直す］を明示操作で提供する。
  - 旧worktree系scopeには tree がないので、追加取得はできない。カード上部に「旧形式: 未収集ファイルは読めません。refreshで新形式（別scope）」と表示し、読めるふりをしない。
  - `turns` / `publications` / `questions` / `asked` / `focus` / `selectedPoint` は、それぞれ会話・変更カード・問い設定・既出キー・宛先・選択に引き継ぐ。
  - ダウングレードすると、旧版は最新の v1（移行前の状態）を読む。v2 で追加した内容は旧版から見えない。これは開示事項として README に書く。
- **保存の見直し**: `/u storage` で、scopeごとに保存量（概算）・会話量・台帳件数・意見件数・object消失の有無を表示する。既存の `reset` / `forget`（確認付き。`src/extension.ts:227-228`）へ誘導する。session file を共有する場合の注意（README:120）もここに表示する。

## 6. 代替案の比較

### A. モデル台帳 + 根拠オンデマンド（推奨）

§4のとおり。

### B. 問い駆動チャット（最小変更）

現在のoverlayとチャット中心の構造を保つ。スクロール・キー・起動・根拠取得（A の段階1〜3）を直したうえで、system prompt を「AIが毎回、予測か説明の問いを1つ返す」ソクラテス式に変える。M番号のmapは残す。

### C. 別プロセスの学習セッション（破壊的）

学習を、別の端末ペイン（tmux分割など）で動く独立した Pi セッションにする。学習用の Pi は、固定snapshotだけを読む読み取り専用toolを持ち、組み込みの編集・実行toolは無効にする。実装セッションとは、片方向のファイル（publication）とhandoffでつなぐ。

| 観点 | A 台帳 + オンデマンド | B 問い駆動チャット | C 別プロセス |
| --- | --- | --- | --- |
| model ownership との整合 | ◎ 主張が型として残り、所有の状態が見える | △ 会話は流れて消え、何を所有したか残らない | ○ 中身はAと同等にできるが、別に設計が必要 |
| 全体 ↔ 局所の往復 | ◎ 台帳とカードと根拠で常に戻れる | △ 全体はmap頼みで、往復はコマンド | ○ Piのtranscriptでは構造化しにくい |
| 認知負荷の調整 | ◎ 1カード1問、足場、問いなしモード | ○ AI任せで揺れやすい | ○ Aと同様にできる |
| スクロール・キー問題 | ○ 自前実装が必要（段階1） | ○ 同じ | ◎ Pi本体のtranscript・検索・キーがそのまま使える |
| 起動の手軽さ | ○ `/u` と補助キー | ○ 同じ | △ 端末ペインの切替が要る。tmuxなどが前提 |
| 会話分離 | ◎ 現行契約を維持 | ◎ 同じ | ◎ プロセス単位で強い。ただしプロセス間の受渡しを新規に設計する必要がある |
| 安全（ツール） | ◎ `tools: []` を維持し、取得は拡張が仲介 | ◎ 同じ | △ 学習AIにtoolを持たせ、組み込みtoolを確実に無効化する必要がある【要検証】 |
| native Pi GPT auth | ◎ 現行の `streamSimple` | ◎ 同じ | ○ 学習セッション自体がPiのモデル選択を使う。GPT以外の禁止を別途強制する必要がある |
| 実装コスト・リスク | 中〜大（段階的に出せる） | 小 | 大（2プロセスの状態整合・設定・QA） |
| 既存資産の活用 | ○ scope・照合・世代管理・handoffを流用 | ◎ ほぼ全部 | △ overlay資産はほぼ捨てる |

**推奨理由**: 目的である model ownership に直接効くのは、「何を理解したか」が型として残り、全体と局所を往復できる A だけである。B の修正項目は A の段階1〜3と同一なので、B を先に出しても無駄にならない。C はスクロールとキーを根本から解決するが、主目的への寄与は A の内容を別プロセスで作り直すことになり、ツール無効化や認証の新たな保証も必要になる。そのため、**A の段階1でスクロール問題が解けなかった場合の退避先**として残す。

**検討して捨てた形**: 図を中心にする案（「見た」と「分かった」が混ざる）、コードツアー（線形で、主導権が作者にある）、点数付きクイズ（AI判定の不確実性を点数で隠してしまう）。

**Aの上に重ねる層（段階5）**: 「変更起点」モード。`publish_understanding`（`src/extension.ts:264-279`）の主張は未検証として扱い、それが動かす主張を台帳上で示して、予測の問いを付ける。AI開発の日常の流れに乗せやすい【仮説】。

## 7. 捨てる機能・変える機能・維持する契約

### 7.1 捨てる・格下げする

| 対象 | 扱い | 理由 |
| --- | --- | --- |
| M番号mapを主表示にすること | 台帳に置き換える。旧mapは読み取り専用カードとして移行 | コード中心で、ルール・境界・理由が型にない（§2.1） |

| 5行ヘッダ | 1行にして、詳細はオンデマンド | 認知負荷と本文面積（§2.6） |

| `reference` の手入力文法を主経路にすること | 根拠チップと自動取得に置き換え、上級者向けに残す | §2.6 |

### 7.2 そのまま残す（中心機能ではない）

- `diagram`（静的HTML）と `diagram preview`（tailnet公開）は、直近のcommitで追加された機能なので黙って捨てない。台帳の書き出しとして残し、同じ escape・CSP・明示公開の契約を守る（`src/diagram.ts`、`src/preview.ts`、`tests/contracts.test.ts:108-116`）。中心の体験からは外す。公開の要否は §9 で確認する。
- 対象選択（`/understand scope`・`targets`・`select_understanding_scope` の確認付き選択）は維持する。

### 7.3 維持する契約（破らない）

1. **学習と実装の会話の分離**: 学習AIへ実装会話・ツール履歴を渡さない（`src/learning.ts:86-89`、`tests/contracts.test.ts:84-92`）。学習会話を実装AIへ自動送信しない。実装側へ渡す経路は、編集と確認を経る `handoff` だけ（`src/extension.ts:235-239`、`tests/extension.test.ts:77-78`）。`publish_understanding` は学習会話を読まない（`src/extension.ts:264-279`、`tests/extension.test.ts:37-78`）。

3. **学習AIのツールなし**: `tools: []`（`tests/contracts.test.ts:92`）。根拠の取得は拡張が仲介する（§4.7）。
4. **secret/path 境界**: `safePath`・`allowedPath`・symlink拒否・repository外拒否・module包含（`src/scope.ts:23-32,62-72,83-99`、`tests/contracts.test.ts:49-63`）。
5. **snapshot一貫性**: 捕捉後に内容を書き換えない（`tests/contracts.test.ts:40-45`）。別時点の内容を混ぜない。履歴系は固定OIDだけを使い、Git replace を無効化する（`src/scope.ts:19`）。HEAD・index・worktree・branchを変更しない（`tests/extension.test.ts:17-35`）。snapshot-as-tree で増えるのは object database への追加だけで、ref追加は同意がある場合に限る（§4.8）。
6. **引用の exact 照合**: 範囲外・不一致・60行超は不採用（`src/learning.ts:43-50`、`tests/contracts.test.ts:65-72`）。対象は台帳の evidence・signature・guards に広げる。
7. **世代管理とキャンセル**: scope・branch・sessionの切替とshutdownで中止し、古い結果を保存しない（`src/extension.ts:54-57,73-82`、`src/learning.ts:92-141`、`tests/extension.test.ts:82-190`）。
8. **branchを考慮したrestore**: `getBranch()` から復元し、放棄されたbranchやrepository違いを混ぜない（`src/learning.ts:27-34`、`tests/contracts.test.ts:74-82`）。
9. **下書きの保持**: 学習側（native Input、remountやCtrl+Tをまたいでも）と通常editorの両方（`tests/pane.test.ts:34-44`、`tests/extension.test.ts:178-184`）。
10. **対象変更の確認**: AI提案による対象選択は、必ず確認UIを経る（`src/extension.ts:138-158,251-263`）。
11. **端末制御文字の除去**（`src/pane.ts:6`、`tests/pane.test.ts:69-72`）と、Overlayが通常editorのmouse handlerを置換しないこと（`tests/pane.test.ts:51-67`）。

## 8. 段階的実装と受入れ条件

各段階は単独で出せるようにする。「振る舞い」の条件は自動テストで確かめ、「学習成果」の条件はユーザー本人の試用（n=1。統計的な主張はしない）で確かめる。

### 段階0: 再現と計測（製品変更なし）

- 内容: §2.2 の検証（ユーザーへの確認、PTY QA でのPgUp・ホイール・送信直後の遡り）と、§2.5 の机上計算の実測（実在repository数件で `evidenceText` の `sent` を記録する）。
- 受入れ: スクロール問題について、原因候補 S1〜S7 のどれが再現したか（あるいはしなかったか）を記録する。送信カバレッジの実測値（中核ファイルが送られているか）を得る。

### 段階1: 移動・スクロール・起動（Bと共通）

- 内容: 会話の独立スクロール、キー体系（§4.6）、KeybindingsManager への準拠、fullscreenのホイール、文脈に応じた下部案内、Esc で一段戻る動作、↑↓＋Enterでの選択（旧mapの点に対して）、`/u` と補完、widget、下書きの保持。
- 振る舞いの受入れ:
  - fullscreen と regular、160x48・120x36・80x24 のそれぞれで、50ターン相当の会話を作り、PgUp を繰り返すと最初の質問文が表示される。PgDn と Ctrl+End で最新に戻れる（PTY）。
  - fullscreen で、ペイン上のホイールでペイン本文が動き、背後の transcript は動かない。ペインの外でのホイールは transcript を動かす。
  - 読んでいる途中に回答が届いても表示位置が動かず、「新しい回答 ↓」が出る。
  - Tab と Shift+Tab で操作対象が循環し、学習の下書きの文字列とカーソル位置は変わらない（`tests/pane.test.ts:34-37` と同じ形式）。
  - どの操作対象でも、`CURSOR_MARKER` は入力欄の行だけにある（`tests/pane.test.ts:18-19` と同じ形式）。
  - `dive N` を打たずに、↑↓とEnterで任意の点を開ける。`dive N` も引き続き動く。
  - Esc で一段ずつ戻り、全体で押すと隠れる。Ctrl+G はどこからでも即座に隠れる。両方とも下書きを保持する。
  - KeybindingsManager で PageUp を再割当てすると、ペインのスクロールもそれに従う。
  - `/u` は、scopeが未選択なら対象選択へ、選択済みなら前回の場所へ開く。Ctrl+Alt+U も引き続き動く（互換）。
  - 下部の案内に、現在の操作対象で使えるスクロールキーが常に出ている（render check）。
  - 既存の分離・下書き・確認系テストがすべて通る。
- 学習成果の確認: 操作面に限る。ユーザーが「全体 → 点 → 戻る」をヘルプなしで3操作以内にできる。過去の回答を自分で探し出せる（自己報告）。

### 段階2: 根拠オンデマンド

- 内容: 領域目録、`need` / `search` の取得ループ、根拠状態の表示（§4.8 の表）、上限、キャンセル、取得記録。まず履歴系scopeに対応する。
- 振る舞いの受入れ（deterministic provider）:
  - 初回送信に含まれないファイルについて質問すると、providerが `need` を返し、拡張が検証して取得する。2回目の呼出しにその内容が含まれ、回答がそれを引用し、ターンに `fetched` が記録される。
  - `.env`・`../x`・symlink・module外・`HEAD:x` 形式の要求は拒否され、拒否理由が「除外」または「範囲外」としてAIと画面に伝わる。
  - 取得のラウンド数・件数・バイト数・時間の上限を超えない。超過分は「未取得」と明記される。
  - 取得中の Ctrl+C で以後の呼出しが起きず、中止がnoticeとして残り、主張は採用されない。取得中にscopeを切り替えると取得ごと破棄され、保存されない。
  - `context.tools` は空のまま（`tests/contracts.test.ts:92` を変更せずに通る）。
  - 旧形式のworktree系scopeで未収集ファイルを要求すると、「作業状態・未捕捉」として拒否され、refreshを案内する。
- 学習成果の確認: 同じ質問セット（ユーザーの実repositoryで10問程度）について、「未取得のため分からない」を含む回答の割合を、段階0の実測と比べる（実モデル、手動）。

### 段階3: snapshot-as-tree と保存形式 v2

- 内容: worktree系scopeのtree化、v2保存、v1からの移行、`/u storage`。
- 振る舞いの受入れ:
  - 捕捉後にworktreeのファイルを編集しても、取得で返る内容は捕捉時のバイト列と一致する（digest）。
  - 捕捉の前後で `git rev-parse HEAD`・`git symbolic-ref HEAD`・`.git/index` のバイト列ハッシュ・`git for-each-ref` の出力・`git status --porcelain` が変わらない。
  - fixture に clean filter を設定しても、それが実行されない（`--no-filters`）。
  - 除外パス（`.env` 等）がtreeに含まれない（`git ls-tree -r` で確認）。
  - objectを削除する状況を模擬すると「object消失」と表示され、内容を捏造しない。
  - v2の保存エントリに source 本文が含まれず、保存1回あたりのサイズが v1 より小さい（閾値は実測で決める）。
  - v1のみのsessionを開くと、旧mapが読み取り専用カードとして見え、会話・publication・設定が引き継がれ、v1エントリが変更されていない。v2を書いた後でも、旧版のrestoreは最新の v1 を読む。
- 学習成果の確認: 該当なし（基盤）。

### 段階4: モデル台帳と問い

- 内容: 台帳の生成（取得ループ込み）、カードと根拠チップ（署名・守るテスト・実装）、所有の状態、問い5種類と足場の調整、照合の4区分、［異議］、理解と意見の区別、意見のhandoff、問いなしモード、system promptの改訂。
- 振る舞いの受入れ:
  - 生成された主張の evidence・signature・guards はすべて exact quote 照合を通る。照合に失敗した主張は採用せず、noticeに残る（`validateMap` と同じ規則）。
  - 所有の状態はユーザー操作でだけ変わる。AIの提案は表示されるが、自動では適用されない。
  - ［意見として記録］した内容は誤りとして数えない。handoff の下書きには、ユーザーが選んだ意見だけが入る。送信には編集と確認が必要で、確認しなければ何も送られない（`tests/extension.test.ts:77-78` と同じ形式）。
  - 照合結果は必ず4区分のいずれかで、引用が付くか、「判定不能」かのどちらかになる。
  - 問いはスキップでき、スキップしても状態が悪化しない。問いなしモードでは問いが出ない。
  - 自由質問は選択中のカードを文脈に含み（既存の選択点の文脈、`tests/navigation.test.ts:43-60` を継承）、Ctrl+O の後は全体への質問になる。
- 学習成果の確認（n=1、未測定の効果を確かめるための手順）:
  1. ユーザーが実際に開発中のrepositoryで、10〜15分使う。
  2. 直後にツールを見ず、ルール3つ・境界2つ・理由1つを書く。ユーザー自身が台帳の根拠と突き合わせる（AIは補助）。
  3. 事前にAIが作り、ユーザーには見せていない「未見の状況」2問に予測で答え、根拠で確かめる。
  4. 仮の変更提案1件について、動く主張を列挙し、AIの分析と比べる。
  5. 任意で、翌日に2の想起を再度行う。
  6. 自己評価:「次にAIへ実装を頼むとき、何を確認すればよいか言えるか」。
  - 判定は効果の主張ではない。設計の改善点を見つけるための観察として扱う。

### 段階5: repository単位の台帳と変更起点

- 内容: 台帳を repository identity 単位で持つ。scopeが変わったら主張を新しいsnapshotで再照合して引き継ぐ（「再確認済み / 根拠が変化 / 未再確認」）。`publish_understanding` を起点にした変更カードを導入する。
- 振る舞いの受入れ:
  - 別snapshotで確認した主張が、再照合なしに「確認済み」と表示されない。
  - 引用行が移動しただけなら「再確認済み（行が移動）」、消えたら「根拠が変化」と表示される。
  - publication は「実装AIの主張（未検証）」として表示され、学習会話は実装側へ出ない。
- 学習成果の確認: 1週間程度の開発の中で、変更カードの予測が何回行われ、その一致・不一致からユーザーが仕様の意見をhandoffしたか（自己記録）。
